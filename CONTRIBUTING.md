# Contributing

## Where things live

- `src/skills/<name>/SKILL.md`: the source of every skill.
- `src/commands/<name>.md`: the source of every command.
- `src/agents/<name>.md`: the source of every custom agent.
- `src/rules/<name>.md`: the source of every rule.
- `src/hooks/<name>/`: the source of every hook, one implementation per tool.
- `src/packs/<name>/`: the source of every orchestration pack.
- `src/guides/<name>.md`: walkthroughs that tie a plugin's pieces into one workflow. List each under `guides:` in one bundle; links are relative to the plugin's `guides/` folder, and the build fails on any that do not resolve.
- `src/mcp/<server>.yaml`: MCP servers that agents and commands use.
- `bundles.yaml`: which plugin each skill, command, agent and guide belongs to. Every one is in exactly one.
- `plugins/`, `rules/`, the three `marketplace.json` files and the tables in `README.md` between `START_`/`END_` markers: generated by `npm run build`. Never edit them by hand.

Edit only `src/`, `bundles.yaml` and the hand-written parts of `README.md`.

## Skill frontmatter

| Key | Rule |
| --- | --- |
| `name` | Required. Matches the folder name: lowercase letters, digits and single hyphens, max 64 characters. Gerund form preferred (`writing-unit-tests`). |
| `description` | Required, max 1024 characters. Third person. Says what the skill does and when to use it, with concrete triggers ("Use when…"). |
| `argument-hint`, `user-invocable`, `license`, `compatibility`, `metadata`, `allowed-tools` | Optional. Copied unchanged to every tool. |

Any other key fails validation, because it would reach tools that don't understand it.

## Command frontmatter

A command is a prompt the user runs on purpose. The build turns it into a skill that the agent never starts on its own.

```yaml
---
name: fix-tests                   # matches the file name; shares a namespace with skills and agents
title: Fix failing tests
description: Diagnose and fix failing tests by addressing root causes ...
agent: test-automation-expert     # optional: hand the work to this agent; keep it in the same bundle
mcp: [playwright]                 # optional
inputs:                           # optional: what the user should supply, with a hint
  testScope: test file, folder, or suite to fix
---
Fix the failing tests in {{testScope}}. ...
```

In the body, `{{name}}` refers to an input. Two more need no declaration: `{{selection}}` (the code the user selected or pasted) and `{{file}}` (the file the user is working on). The validator fails on undeclared placeholders and warns on unused inputs.

## Agent frontmatter

An agent says what it may do, not which tool names it uses. The build translates that for each tool.

```yaml
---
name: test-code-reviewer          # matches the file name
title: Test Code Reviewer         # optional, shown in the README and in Copilot
description: Reviews automated test code for anti-patterns ... Use when ...
capabilities: [read, search, edit, web, todo]
mcp: [playwright]                 # optional, servers from src/mcp/
---
```

| Capability | Lets the agent | Copilot | Claude Code | Codex |
| --- | --- | --- | --- | --- |
| `read` | read files | `read` | `Read` | always on |
| `search` | search the project | `search` | `Grep`, `Glob` | always on |
| `edit` | change files | `edit` | `Edit`, `Write` | told not to edit when absent |
| `execute` | run commands | `execute` | `Bash`, `PowerShell` | shell turned off when absent |
| `web` | fetch and search the web | `web` | `WebFetch`, `WebSearch` | inherited |
| `agent` | hand work to other agents | `agent` | `Agent` | inherited |
| `todo` | keep a task list | `todo` | task tools | inherited |
| `ide` | use editor features | `vscode` | none | none |

Grant the fewest capabilities the job needs. Don't pin a model.

## Rule frontmatter

```yaml
---
description: Playwright E2E test rules ...
applyTo:
  - 'tests/e2e/**/*.spec.ts'
---
```

Scope `applyTo` to the files the rules are about; the validator warns on `**`. Rules don't belong to a bundle: every rule is published under `rules/` for each tool.

## Orchestration packs

```
src/packs/<name>/
├── pack.yaml              # name, title, description, orchestrator: <agent name>
├── GUIDE.md               # optional: how the workflow runs, step by step
└── agents/<agent>.md      # agent frontmatter, plus a `copilot:` block
```

Pack agents use the same frontmatter as other agents, with two additions:

- `title` is required. It is the agent's name in Copilot.
- `copilot:` holds Copilot-only fields, copied into the Copilot build as they are: `handoffs`, `agents`, `user-invocable`, `argument-hint`, `target`, `mcp-servers`. `handoffs[].agent` and `agents` refer to other agents by `title`, and must resolve inside the pack.

Agent names share one namespace with every other agent, because Codex keeps all agents in one folder. Prefix them with a short pack name (`uiapi-test-planner`).

In Claude Code and Codex, subagents can't start other subagents, so the build turns the orchestrator into a command named after the pack. That command runs in the main conversation and maps every `title` used in the instructions to the agent names to call. Write orchestrator instructions that delegate by agent title ("ask the Test Planner to…"), not by a Copilot tool name.

## Hooks

Each tool calls hooks with different events, payloads and output channels, so a hook has one implementation per tool rather than a shared source:

```
src/hooks/<name>/
├── hook.yaml              # name, title, description, hosts: [copilot, claude]
├── <config>.json          # optional, shared: copied next to each tool's scripts
├── copilot/               # hooks.json (camelCase events) + scripts/*.sh and *.ps1
└── claude/                # hooks.json (PascalCase events) + a Node.js script
```

- **Claude Code:** each hook is published as its own plugin. Run scripts as `"command": "node", "args": ["${CLAUDE_PLUGIN_ROOT}/hooks/<script>.cjs", ...]`, so the same file works on every OS without a shell or `jq`. Claude sees SessionStart stdout; after a tool call, context reaches Claude only through `hookSpecificOutput.additionalContext`.
- **Copilot:** published as a folder to copy into `.github/hooks/<name>/`. Set `cwd` in `hooks.json` to that path.
- **Every hook:** exits 0 when unsure and never blocks on its own failure.

Test a Claude Code hook by piping a sample event into it. Point `cwd` at a scratch directory, because hooks may write logs under it:

```sh
dir=$(mktemp -d)
echo "{\"cwd\":\"$dir\",\"tool_name\":\"Edit\",\"tool_input\":{\"file_path\":\"$dir/tests/a.spec.ts\"}}" \
  | node src/hooks/always-on-skills/claude/always-on-skills.cjs post-tool
```

## Adding or changing something

1. Edit the file under `src/`. File or folder names must match the `name` field.
2. If you added a skill, command or agent, put it in one bundle in `bundles.yaml`.
3. Run:
   - `npm install` (first time only)
   - `npm run validate`: checks frontmatter and bundle membership
   - `npm run build`: regenerates `plugins/`, `rules/`, the marketplace files and the README tables
   - `npm run check`: confirms the generated files are up to date
4. Commit the source change and the regenerated files together. CI runs `npm run lint`, which fails if they differ.

## Guidelines

- Write skills, agents and rules that work in every supported tool. Don't name Copilot, Claude Code or Codex unless the asset is about them; the validator warns when a skill does.
- Keep `SKILL.md` under 500 lines and move detail into `resources/`.
- `description` says what the skill does and when to use it, with concrete triggers.

## Writing for agents

These rules apply to every skill, agent, command and rule. The README's [Inspiration](README.md#-inspiration) section lists the collections they draw on.

- **The description is the trigger.** Lead with what the asset does, then one trigger per distinct situation. Merge synonyms that describe the same situation into one trigger, and never summarise the workflow, or the agent follows the summary instead of the skill. If agents skip the skill because they think they can manage alone (a pasted diff, a pasted stack trace), say the skill applies in that case too.
- **Every step ends on a completion criterion.** Write "the test goes red on this bug" rather than "understand the bug". The stricter the bar ("every changed line accounted for"), the more thorough the work it gets.
- **Write the target, not only the ban.** "Wait for the response the assertion depends on" works better than "don't use `waitForTimeout`". Keep a hard ban only when it can't be phrased positively, and pair it with what to do instead.
- **Discipline skills answer the excuses.** Where an agent is tempted to cut corners (TDD, flaky tests, coverage, waivers, review), add a "Common Rationalizations" table (excuse, then the factual reality) and a "Red Flags" list of signs visible in a diff or transcript.
- **Write the procedure, not the workaround.** A step that only makes sense for one model or one host's tool name doesn't belong in a skill. Describe the capability ("run the focused test"), not the tool.
- **Cut sentences that change nothing.** If removing a sentence wouldn't change what the agent does, delete it. Don't restate what `package.json`, the config or `--help` already says.
